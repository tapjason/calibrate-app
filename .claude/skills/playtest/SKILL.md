description: Playtest the web build - web-playtester (does it work) then blind-playtester runs, one persona each from docs/app-profile.md §10, one after the other in one browser, synthesised against the docs into a ranked findings file in docs/design/research/. Starts the web server; needs the playwright MCP. Never counts as an iPhone check.
argument-hint: "[optional: focus (e.g. stress, appeal), personas, sizes, or 'blind only']"

---

Playtest the current build. Focus: $ARGUMENTS (if empty: everything changed since the last `docs/design/research/playtest-*.md`).

1. **Ready.** `git status` (the playtest runs whatever is on disk; note uncommitted changes). Read `docs/tooling-notes.md`, `docs/app-profile.md` §9, §10 and §18, and the last playtest file (what was flagged before). Run `bash scripts/web-serve.sh start` and wait for it to report up (the first bundle is slow). The server doesn't hot-reload: if code changed since it started, `stop` then `start`. If it can't start, read `.tooling/expo-web.log`, fix a build error if it's ours, otherwise stop and tell the user the playtest is owed.
2. **Does it work.** Unless the focus says "blind only", delegate to `web-playtester` with the focus, the checks from the step or decision rows, and the start states. Wait for its report. If it's BLOCKED, stop and tell the user what to run.
   - **A stress focus** ("stress", "UI stress", "edges", or a device report like the 2026-11-12 Dynamic Island one) adds a stress pass to that brief, before any blind run. Start states: the §9 `stress` and `years` profiles, and a fresh install. Every main screen and sheet (Today, Insights, History, You, Log, Resolve, the prediction details, Share, Categories, Practice, Scoring, the Paywall) at 320 × 568, 402 × 874 and 440 × 956 (portrait only: the app doesn't rotate on iOS), in light and dark, at zoom 1 and 2. Check each for: anything clipped, overlapping or cut mid-word or mid-character; the close or back control on screen and reachable at every size, including after scrolling; long words, links, Arabic, Japanese and Ge'ez titles wrapping whole; four-digit counts; the 36-card list scrolling with the hero and reminder ask in place. Then the impatient checks: double-tap Save, swipe or close a sheet mid-save, reload mid-flow, back navigation from each sheet. The clock and device stand-ins of §9 (a time zone east and west, a clock at 23:55 across midnight, CPU throttled 4×, offline after the app has loaded, then in-app navigation, since the web build can't load a page offline) need `browser_run_code_unsafe`, which `web-playtester` doesn't have: the main session runs them itself after the agent reports, then closes the page (`browser_close`) so an installed clock can't leak into the blind runs. Besides its findings, the report lists every edge only the iPhone can show (the Dynamic Island and other safe areas, native sheet presentation and its gestures, real Dynamic Type), for `/device-check`.
   - **An appeal focus** ("appeal", "UX", "first impressions", "would people want it") is about whether people would choose, enjoy, return to and recommend the app, not whether it holds up. Read `docs/playtest-appeal.md` first: its factors choose the tasks, its block B goes into every brief, its synthesis section shapes step 6. The `web-playtester` brief shrinks to a health check of the start states the cast needs (a fresh install through the Warm-up and a first log, each profile loading, the card's text share), so the blind runs don't trip on a broken path.
3. **Choose the cast** by profile §10's "Choosing a round's cast": the personas the focus needs, then fill to six to eight so the round spreads across the diversity axes, with one wildcard drawn at random. If the axes leave a gap no persona covers, write a new row into §10 first. For an appeal focus, use §10's "Choosing an appeal round's cast" instead (tech literacy L1–L5, age, region, money, taste, how they found it). Read the persona tables of the last two `playtest-*.md` files first, so nobody returns without a reason. Write the cast as a table (persona, axis values, start state, screen) before any run; it goes into the round's Method.
4. **Write each brief** self-contained, because `blind-playtester` can't read files:
   - **The person**, in a paragraph: who, what they want from the app, where and how they use their phone (one hand, a dark room, a two-minute break), their English (a second-language reader names the words they wouldn't know), and how judgemental to be.
   - **What they know:** only what the App Store page would tell them. Never what a screen is for or where a control is. For an appeal focus, also how they found it, in their terms (a friend's card gives the text the friend sent, as `docs/playtest-appeal.md` says), and block B from that file, word for word.
   - **Start state, screen, appearance, stand-ins** (zoom, Reduce Motion, keyboard and screen reader) and the URL from `bash scripts/web-serve.sh status`. The start state is a §9 playtest profile wherever one fits; the brief describes it in the persona's own terms ("you've used it every day for three weeks"), never by its id.
   - **Tasks as goals** in the persona's words ("make sure it reminds you", "find out where you're most off"), four to seven of them, in the order that person would try them. No button or screen names. Include at least one findability task (a setting or number to locate) and one recovery task (undo a mistake). For an appeal focus, tasks are what the person would do with a new app instead ("see if it's any good", "try it on something real from your week", "decide whether it's worth keeping"), with one about their own life, one about telling or showing someone, and one about keeping it or paying. Keep your own success criteria for each task out of the brief and use them in step 6.
   - **An interruption** where it fits the person: a reload mid-flow, back navigation, or "you're called away" (the brief says when; the tester reloads or navigates away and comes back).
   - **Three comprehension questions** for the end, about what the persona saw ("What does the number on your card mean?"), answered in their own words without going back to look.
   - The screenshot names `playtest-<yyyy-mm-dd>/run<n>-<moment>.png`, and the rules: no sign-in, no purchase, no erase, stay on localhost.
5. **Run them one at a time** (one browser, one database). Between runs, prepare the start state yourself: a fresh install per profile §9, or a playtest profile on `/dev/seed` (two taps on `dev-seed-profile-<id>`, then wait for `dev-seed-profile-status` to say it loaded). A state no profile gives becomes a new profile in `src/dev/playtestProfiles.ts`, with its test, rather than a one-off script. Later runs may keep what earlier runs left, and say so. Stand-ins the agent can't set (colour vision, offline), you set on the page before delegating; say in the brief what they see. Then delegate to `blind-playtester` and wait.
6. **Synthesise against the docs.**
   - Check every finding against the code (`Grep`/`Read`). Drop what is web-only (profile §18, `docs/tooling-notes.md`: the draft guard, `hitSlop`, the VoiceOver adjustable, the iOS switch, the dev overlay, focus handling) into a "Web-only, so not ranked" paragraph.
   - **Usability numbers:** a table of tasks by run (done / done with help of a wrong turn / gave up), the ease scores (median per task), and the expectation mismatches. A task under 5 on ease, or given up by two runs, is a finding even if nobody complained.
   - **Comprehension:** compare each answer with what the app means (`CLAUDE.md`). A wrong answer is a finding about the screen, not the tester.
   - **Rank** the rest: P1 breaks and record risks (§5 ids first), P1 hierarchy and story, P2 polish, P2 consistency, P2–P3 structure, accessibility on iOS too. Within a group, order by severity, then by how many runs hit it. Give each the runs that hit it and the axis that exposed it ("second-language", "tremor"), so a finding only one kind of person hits isn't mistaken for noise.
   - Mark each "no decision needed" or "needs the owner" (anything that changes what a screen says or how it's arranged, or a decided D number).
   - **For an appeal focus,** add `docs/playtest-appeal.md`'s synthesis: the appeal table, the split by tech literacy, age, arrival and culture, the mood curve, the words, and its ranking order. Never report a disappointment share or a price as a market number.
7. **Record** a new `docs/design/research/playtest-<yyyy-mm-dd>.md` in the established shape: the banner "Raw findings, <date>. … Where they differ, `CLAUDE.md`, `DESIGN_SYSTEM.md` and `UI_ROADMAP.md` win."; Method, with the cast and its axis values, the wildcard's draw and the stand-ins; the persona table with verdicts and scores; the usability table and comprehension results (and for an appeal focus, the appeal table, the splits and the mood curve); What held up; Ranked findings. Commit it as `docs: <nth> blind playtest round (<focus>), raw findings ranked`.
8. **Reply** with the scores, the task success and ease summary (for an appeal focus, also who would keep it, miss it, post it or pay, by group), the top findings, which groups can be fixed without a decision, and which need the owner. Leave the server running if the user is mid-session (say so); stop it otherwise. If the server was stopped by the system (low memory), say so and don't restart it unasked.

Never run two browser agents at once, never let a blind run see the repo, and never count a web pass as an iPhone pass.
